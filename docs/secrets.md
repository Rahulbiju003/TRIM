# Secrets Management

API keys and the `TRIM_API_KEY` should not be stored in plaintext `.env` files on shared infrastructure. This document covers production-grade alternatives.

---

## Local development

For a single developer's local machine, a plaintext `.env` is acceptable with two requirements:

1. The file must not be committed to version control. Verify:
   ```bash
   grep -q '.env' .gitignore || echo "WARNING: .env is not in .gitignore"
   ```

2. Permissions must restrict access to the owning user:
   ```bash
   chmod 600 .env
   ```

3. Inline comments corrupt values when loaded via `podman run --env-file`. Use only full-line comments:

   ```bash
   # Good — comment on its own line
   GEMINI_API_KEY=AIza...

   # Bad — inline comment corrupts the value
   GEMINI_API_KEY=AIza...   # Google Gemini
   ```

## Podman secrets (local container)

Podman has a native secret store that avoids writing credentials to disk as plaintext.

### Create secrets

```bash
printf 'AIza...' | podman secret create gemini_api_key -
printf 'your-trim-key' | podman secret create trim_api_key -
```

### Use secrets at runtime

```bash
podman run -d \
  --name trim-worker \
  -p 8080:8080 \
  --secret gemini_api_key,type=env,target=GEMINI_API_KEY \
  --secret trim_api_key,type=env,target=TRIM_API_KEY \
  -e WORKER_MODEL=gemini/gemini-2.5-flash \
  -e SHUNT_MIN_LINES=350 \
  -e SHUNT_TIMEOUT_SECONDS=45 \
  -e SHUNT_MAX_BYTES=400000 \
  -e WORKER_PORT=8080 \
  trim-worker
```

Secrets are injected as environment variables at container start. They are never written to disk in plaintext form.

### List and remove secrets

```bash
podman secret ls
podman secret rm gemini_api_key
```

## Environment injection (CI/CD and server deployments)

On a remote server, inject secrets from your environment rather than a file:

```bash
podman run -d \
  --name trim-worker \
  -p 8080:8080 \
  -e WORKER_MODEL=gemini/gemini-2.5-flash \
  -e GEMINI_API_KEY="$GEMINI_API_KEY" \
  -e TRIM_API_KEY="$TRIM_API_KEY" \
  -e SHUNT_MIN_LINES=350 \
  -e SHUNT_TIMEOUT_SECONDS=45 \
  -e SHUNT_MAX_BYTES=120000 \
  -e WORKER_PORT=8080 \
  trim-worker
```

Load the values into the shell session from a secret manager before running this command.

## HashiCorp Vault

```bash
# Authenticate and fetch secrets into the shell environment
export GEMINI_API_KEY=$(vault kv get -field=api_key secret/trim/gemini)
export TRIM_API_KEY=$(vault kv get -field=key secret/trim/auth)

podman run -d --name trim-worker \
  -e GEMINI_API_KEY="$GEMINI_API_KEY" \
  -e TRIM_API_KEY="$TRIM_API_KEY" \
  ... trim-worker
```

## Google Secret Manager

```bash
export GEMINI_API_KEY=$(gcloud secrets versions access latest --secret=trim-gemini-key)
export TRIM_API_KEY=$(gcloud secrets versions access latest --secret=trim-api-key)

podman run -d --name trim-worker \
  -e GEMINI_API_KEY="$GEMINI_API_KEY" \
  -e TRIM_API_KEY="$TRIM_API_KEY" \
  ... trim-worker
```

## AWS Secrets Manager

```bash
export GEMINI_API_KEY=$(aws secretsmanager get-secret-value \
  --secret-id trim/gemini-api-key --query SecretString --output text)
export TRIM_API_KEY=$(aws secretsmanager get-secret-value \
  --secret-id trim/api-key --query SecretString --output text)

podman run -d --name trim-worker \
  -e GEMINI_API_KEY="$GEMINI_API_KEY" \
  -e TRIM_API_KEY="$TRIM_API_KEY" \
  ... trim-worker
```

## What the hook scripts contain

Hook scripts generated by `./setup.sh --install` contain:

- `WORKER_URL` — the server address (not a secret)
- `TRIM_API_KEY` — baked in at install time (sent as `X-TRIM-Key` header)

The `TRIM_API_KEY` in the hook script grants access to submit files for summarisation only. It does not grant access to the underlying LLM API key, which remains on the server.

If the `TRIM_API_KEY` is rotated, re-run `./setup.sh --install` on each developer machine.
